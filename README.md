# hortcmd

A file commander in the style of Norton Commander, built with **Rust** + **Tauri v2**.
Two panes, a function-key bar (F3–F8), tabs, and the same interface for local
folders and remote servers.

Architecture and design details: see [Concept.md](Concept.md).
Directory freshness and resource limits: [directory refresh](docs/directory-refresh.md).
Contributing: see [CONTRIBUTING.md](CONTRIBUTING.md).

## What it does

Implemented and in use:

- **Two panes, tabs, keyboard-first.** TC key model (F3 view, F4 edit, F5 copy,
  F6 move, F7 new folder, F8 delete), pattern selection, four view modes, a
  quick filter, a draggable splitter, per-pane navigation history.
- **File operations** with a progress window: copy, move, delete, create, batch
  rename, and an optional **failure-safe** mode that stages and commits so an
  interrupted overwrite cannot lose the old destination.
- **Archives**: browse and extract ZIP, tar, tar.gz, tar.xz and 7z (password
  protected included); packing produces ZIP.
- **Remote locations**: SFTP, FTP/FTPS, SMB and WebDAV, browsed and transferred
  through the same UI as local folders — see the [provider support](#provider-support)
  matrix for exactly which actions each one offers.
- **An SSH terminal** on an SFTP connection, sharing its authenticated session.
- **Credentials** in the OS keychain, or optionally in a portable KeePass
  (`.kdbx`) file.
- **Search** (name, content, duplicates, empty folders, large files), directory
  and file comparison, properties with permissions, ownership, checksums, Git
  status and Finder tags.
- **German and English**, switchable at runtime, including error messages.

The **MCP server** is implemented under [TICKET-041](tickets/done/041-mcp-interface.done.md),
with final integration acceptance still in progress. It is disabled by default;
see [MCP setup and verification](docs/mcp.md). The **plugin system**
([TICKET-201](tickets/201-plugin-api-contract.md)–208) remains planned.

## The pieces

Where to look when you need to change something:

| Component | Lives in | Owns |
|---|---|---|

| **Commands & keyboard** | `src/features/commander/` | The command table every surface reads, the global key handler, the action runners |
| **IPC client** | `src/ipc/` | `client.ts` is the only import path; `invoke.ts` the transport, `events.ts` the event routing, `demo.ts` the browser fallbacks, `domains/*.ts` the commands, `bindings/` generated by ts-rs |
| **State** | `src/store/` | Zustand stores; `store/panes/state.ts` holds the pure pane transitions, `capsStore.ts` the capability cache |
| **Backend commands** | `src-tauri/src/commands/fs/` | Thin adapters: check the capability, resolve the address, delegate |
| **Transfer engine** | `src-tauri/src/commands/fs/transfer/` | Planning and commit, progress, the sequential and parallel copy paths |
| **VFS** | `src-tauri/src/vfs/` | The `Provider` trait, the address parser and scheme registry, one module per protocol, and the capability contract (`caps.rs`) |
| **Network sessions** | `src-tauri/src/net/` | Connection profiles, the connect lifecycle, SSH, host keys, the terminal |
| **Credentials** | `src-tauri/src/net/credentials.rs` | The `CredentialStore` trait, the OS keychain and the KeePass backend |
| **Errors** | `src-tauri/src/errors/` | The `AppError` contract, the codes, redaction |

**Following a remote copy through the layers.** F5 in the UI calls
`runCopy` (`features/commander/fileOps.ts`), which asks the capability contract
whether both ends may do it (`store/capsStore.ts` → `location_capabilities`) and
then `startTransfer` (`ipc/domains/transfers.ts` → `copy_entries`). The backend
resolves both addresses through `vfs::resolve`, which looks the connection up in
`net::session`'s registry — the provider there was built at connect time from a
profile plus a secret from `net::credentials`. The engine
(`commands/fs/transfer/engine.rs`) measures, settles collisions, and streams
through the provider's `open_read`/`create_write`, reporting `fs-progress` and
finishing with `fs-done`.

## Provider support

Local and remote share one interface, but not one feature set: the VFS
`Provider` trait covers browsing, preview, transfers, create, rename and delete;
everything else still runs against `std::fs` or a platform API and therefore
works on **local** addresses only.

The backend states this per address (`vfs/caps.rs`, TICKET-031) and the frontend
disables what a location cannot do. The full matrix is in
[Concept.md § Location capabilities](Concept.md) — in short:

| | local | SFTP | FTP/FTPS | SMB | WebDAV |
|---|---|---|---|---|---|
| Browse, preview | ✅ | ✅ | ✅ | ✅ | ✅ |
| Copy, move, create, delete | ✅ | ✅ | ✅ | ✅ | ✅ |
| SSH terminal | – | ✅ | – | – | – |
| Trash, "open with", system open, local terminal | ✅ | – | – | – | – |
| Search, comparison, archives, checksums, folder size | ✅ | – | – | – | – |
| Git status, volume info, properties | ✅ | – | – | – | – |
| Permissions / ownership | Unix | – | – | – | – |
| Quick Look, Finder tags | macOS | – | – | – | – |

A dash means *the command implementation is local-only*, not that the protocol
could never do it. Each future ticket that routes one through the VFS moves one
row. The matrix is checked against `vfs/caps.rs` by `npm run check:docs`, so it
cannot drift from the code.

## Security

**SSH host keys** (TICKET-028). Every SSH connection — SFTP browsing and the
integrated terminal, which share one session — authenticates the *server*
before a password, key signature or agent signature is sent. The presented key
is matched against the user's own OpenSSH `known_hosts` files (read only, never
rewritten) and a hortcmd-managed store at `<config>/hortcmd/known_hosts`:

- **Known key** → connects without a prompt.
- **Unknown host** → the connection stops *before* authentication and the
  connection manager shows host, port, key type and the SHA-256 fingerprint.
  *Trust and connect* stores that exact key and retries; cancelling sends
  nothing.
- **Changed key** → hard failure showing both the stored and the presented
  fingerprint, with no one-click bypass. Replacing a trusted key is an explicit
  step in the connection manager (*Drop host key…*), which only clears hortcmd's
  own store and reports — never edits — conflicting entries in your
  `known_hosts`.

A conflict in *either* source blocks the connection; a match in one never
overrides it.

**Failure-safe transfers** (TICKET-029, Settings → File operations, **off by
default**). Normally a copy writes straight to the final name and an accepted
overwrite deletes the old destination first, so a failed or cancelled overwrite
can lose it. With the setting on, each top-level source is copied into a hidden
staging entry *on the destination store* and published with a single rename:

- The final name appears only once the copy is complete and verified.
- An existing destination survives until the replacement is in place — via the
  provider's atomic replace where it has one, otherwise a backup rename that is
  undone if the commit fails.
- A copy-based move deletes its source only after the destination is committed.
- Cancellations and failures remove only the staging entry.

The tradeoff is space: staging needs room for the copy next to the target. Safe
mode never silently degrades — a destination that cannot commit a staged entry
fails the transfer and says so. Remains of an interrupted run
(`.hortcmd-stage-*`, `.hortcmd-backup-*`) are reported, never deleted without
asking: such an entry can hold the only copy of a file.

**WebView trust boundary** (TICKET-030). The window that renders previews is the
same window that can invoke every Rust command, so untrusted file content is
kept away from it in layers:

- **Content Security Policy** in `tauri.conf.json` — production starts from
  `default-src 'self'` with no `http:`, `https:`, `*` or `unsafe-eval`. `data:`
  is allowed for `img-src` only (generated image previews); `'unsafe-inline'` is
  confined to `style-src` (React/Radix inline styles, dynamic dialog sizing).
  `devCsp` is separate and covers only the Vite origin and HMR, so production
  inherits nothing from it.
- **Navigation policy** — the main WebView accepts only the app document
  (`tauri:` / `http://tauri.localhost`, plus `http://localhost:1420` in dev).
  Everything else is refused; blocked attempts are logged in development with
  the URL alone.
- **Links** in rendered Markdown never navigate the WebView: the click is
  swallowed and a validated `http(s)` URL goes to the system browser through
  `open_external`, which re-checks the scheme. `open_path` stays the file entry
  point and is never used as a URL escape hatch.
- **Sanitization** — Markdown is rendered through DOMPurify with an explicit
  element/attribute allowlist and an `http(s)`-or-fragment URL rule (relative
  hrefs are stripped too: they are same-origin and would otherwise replace the
  running app). Highlighted source is escaped by highlight.js or by hand.

The remaining boundaries are documented here so that what is *not* protected is
as visible as what is:

**IPC surface.** Everything the WebView can reach is one `invoke` away — there
is no per-command privilege level, and the frontend is not a security boundary.
The Tauri permissions in `src-tauri/capabilities/default.json` are deliberately
minimal (window geometry and closing, one entry per caller); the app's own
commands are guarded by the capability contract and by argument validation in
Rust, never by the UI hiding a button. Path arguments are resolved and checked
in the provider, so a crafted path from a compromised WebView cannot escape the
addressed store — but a compromised WebView still has the user's own file
access. That is why sanitization and the navigation policy above matter.

**Stored credentials.** Connection profiles are plain JSON in the app config
directory (`HORTCMD_CONFIG_DIR` moves the whole directory, for a portable
install) and never contain a secret. Passwords, passphrases and the KeePass
master password live in the credential store, keyed by connection id:

- **OS keychain** (default) — macOS Keychain, Windows Credential Manager, Linux
  Secret Service. Protection is exactly the platform's: while your desktop
  session is unlocked, any program running as you can ask for the same entries.
- **KeePass** (`.kdbx`) — a portable alternative that stays locked until you
  unlock it, and can re-lock. Its master password is only stored in the OS
  keychain if you ask for that, which of course trades the isolation back.

hortcmd does not encrypt anything itself, and secrets are held in plain memory
for the life of a connection (no zeroing on drop, no protection against a core
dump or a debugger attached to the process). On Linux without a running Secret
Service, saving fails and says so — there is no plaintext fallback.

**Browser storage.** Settings, the session, the folder history, dialog sizes and
the window geometry live in the WebView's `localStorage`, in plain text and
unencrypted. No secret is ever written there — not a password, not a passphrase,
not a key — and the preferences export refuses a file carrying a field whose
name suggests one rather than silently stripping it. Everything stored is
versioned, migrated and validated on every load, with the original kept aside
when it has to be repaired (Concept.md § Persisted state); the reset in
Settings → General lists exactly what it clears before it does it.

**Remote transport.** Certificates are validated by the platform TLS stack and
there is no "continue anyway": an invalid or expired certificate fails the
connection. There is also no certificate pinning and no trust-on-first-use for
TLS — unlike SSH host keys, a certificate that a system-trusted CA vouches for
is accepted without asking.

A self-hosted server whose certificate comes from the operator's own CA is the
one case the platform store cannot cover, and the answer is an *additional*
anchor rather than a weakened check — the same shape as `CURL_CA_BUNDLE` or
`NODE_EXTRA_CA_CERTS`:

```bash
HORTCMD_EXTRA_CA=/path/to/ca.pem
```

Every certificate in that file joins the roots for FTPS and WebDAV. Hostname,
expiry and chain are still checked, an unknown issuer still fails, and a bundle
that is named but unreadable is an error rather than a silent fallback to fewer
anchors than you asked for.

- **SFTP** — encrypted, with the host-key verification described above.
- **FTPS** — explicit (`AUTH TLS`) or implicit; plain **FTP** sends credentials
  and data unencrypted and is offered only because servers still require it.
- **WebDAV** — HTTPS with validated certificates. Port 80 addresses are treated
  as plain HTTP and are equally unencrypted.
- **SMB** — hortcmd uses the `smb` crate's defaults and negotiates signing and
  encryption with the server; it cannot currently *require* either. Treat an SMB
  share on an untrusted network accordingly.

**Not implemented:**

- **Plugins** ([TICKET-201](tickets/201-plugin-api-contract.md) …
  [TICKET-208](tickets/208-reference-demo-plugin.md)) —
  there is no plugin host, no loader, and no extension point. Nothing in this
  repository executes third-party code.
The optional MCP endpoint binds only to loopback and requires its keychain-backed
bearer token, enabled capability tiers and allowed roots. Writes require in-app
approval by default. See [MCP security and configuration](docs/mcp.md).

Reporting a vulnerability: open an issue if it is low-risk, otherwise contact
the maintainer directly rather than filing publicly.

## Development

```bash
npm install
npm run dev            # browser only: demo data, no Rust (see below)
npm run tauri dev      # the real app: Vite + Rust backend
```

### Browser-demo mode

`npm run dev` serves the frontend with **no Tauri runtime**. The IPC client
notices and answers from `src/ipc/demo.ts` instead of invoking commands, which
makes layout and interaction work possible without a Rust build — and lets the
whole frontend test suite run in CI with no native process.

It exercises the real stores, the real components and the real keyboard model.
It does **not** exercise:

- any actual file system — listings, sizes, previews and properties are
  fabricated, and nothing is ever written or deleted;
- the transfer engine, including staging, commit, collisions and cancellation
  (the demo simulates progress events);
- any remote protocol, connection lifecycle, or the SSH terminal;
- credential storage, host-key verification, or anything else in `src-tauri/`;
- the production Content Security Policy and navigation policy, which exist
  only in the packaged WebView;
- the capability contract's *real* answers — the demo returns one deterministic
  local set, so remote restrictions cannot be seen there.

In short: everything above the IPC boundary is real; nothing below it is. Use
`npm run tauri dev` for anything that touches the backend.

## Packaging

```bash
npm run tauri build
```

Produces a platform bundle in `src-tauri/target/release/bundle/` (`.app`/`.dmg`
on macOS, `.deb`/`.AppImage` on Linux, `.msi`/`.exe` on Windows). Signing and
notarization are not configured — TICKET-222 owns that.

A packaged build differs from `tauri dev` in two ways that matter: it uses the
production CSP rather than `devCsp`, and it serves the app document over the
custom protocol instead of the Vite origin. Anything touching the WebView trust
boundary has to be checked in a packaged build, not only in dev.

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `Invalid hook call` right after adding a dependency | Vite pre-bundled the old dependency set. Stop the dev server and start it again. |
| A dialog opens empty in the browser but works in the app | It needs a backend answer the demo does not fabricate. Use `npm run tauri dev`. |
| `check:bindings` fails | A Rust type changed. It already regenerated the bindings — commit them. |
| `check:docs` fails on the provider matrix | `vfs/caps.rs` and the matrix in Concept.md disagree. The code is the source of truth. |
| `check:boundaries` reports a cycle | Something imports upwards. The failure prints the rule and why it exists. |
| Linux: "credential store is not available" | No Secret Service is running. Start a keyring, or switch to the KeePass backend in the connection manager. |
| A live protocol test fails immediately | Its server is not running. The Docker command is in the doc comment above the test. |

## Tests and CI

`npm run check` is the whole gate, and it is exactly what
`.github/workflows/ci.yml` runs — a red build is reproducible locally with the
same command. In order:

```bash
npm run check:fmt         # cargo fmt --check
npm run check:clippy      # clippy, all targets and features, warnings are errors
npm run check:rust        # cargo test --locked
npm run check:bindings    # ts-rs bindings match the Rust types
npm run check:errorcodes  # the TypeScript error codes match the Rust ones
npm run check:boundaries  # no import cycles, no upward imports
npm run check:docs        # links, documented commands, the provider matrix
npm run typecheck         # tsc --noEmit
npm test                  # vitest
npm run build             # production bundle
npm run check:bundle      # chunk composition and the eager budget
```

Rust first: it is the slowest half, and a broken backend makes the frontend
result meaningless.

**Layout.** Tests live beside the module they cover (`src/lib/path.test.ts`,
`src/store/panesStore.test.ts`, …). `src/test/` holds only the shared
machinery: `setup.ts` (localStorage shim plus the reset of DOM, timers, mocks,
Tauri harness and Zustand stores between tests), `tauri.ts` (the typed IPC
stand-ins) and `fixtures.ts`.

**Choosing a mode.** The IPC client behaves differently with and without a
Tauri runtime, and both are real. A test says which it wants:

```ts
import { useDemo, useTauri } from "@/test/tauri";

useDemo();                                   // browser build: demo fallbacks
const tauri = useTauri({ commands: { … } }); // mocked runtime + event pushes
```

`useDemo()` is the default, so the frontend suite needs no native process —
which is what lets it run in CI. An unmocked command fails loudly rather than
returning `undefined`.

**The protocol harness.** The remote providers are tested against real
servers — SFTP, plain FTP, explicit and implicit FTPS, SMB with signing, and
WebDAV over HTTP and HTTPS. The servers are not anyone's infrastructure: the
harness builds them from pinned base images, generates a password, a private CA
and an SSH host key for the run, seeds every one of them with the same tree,
runs the suite, and deletes all of it again — including after a failure, and
after Ctrl+C.

```bash
npm run test:harness
```

That is the whole prerequisite list: Docker, and nothing published beyond
`127.0.0.1`. Runs are isolated by a run id, so two can go at once.

The suite answers three questions: whether every provider implements the same
contract (listing, stat, streaming, create/rename/delete, staging, traversal,
error mapping), whether the engine moves bytes correctly in all four directions
(local↔remote, within one server, and between two *different* protocols), and
what happens when the server dies mid-copy, the certificate does not verify, or
the host key changes. `harness/` holds the whole thing;
`.github/workflows/protocol-harness.yml` runs it weekly and on demand, and
uploads the redacted service logs when it fails.

The tests are `#[ignore]`d and **skip** rather than fail without the harness, so
`cargo test -- --ignored` by hand says what to run instead of producing a wall
of connection errors.

**Keychain tests.** The OS-keychain and KeePass interop tests (`*_live` in
`net/credentials.rs`) stay local-only: they need a desktop keyring and an
interactive session, which is exactly what CI does not have.

**Architecture boundaries.** `scripts/check-boundaries.mjs` walks the import
graph and fails on an import cycle or on a violation of the documented layer
rules — `lib/` stays leaf, the IPC foundation sits below its domain clients,
translations are data, the pure pane transitions do not depend on the store that
uses them, and the Rust transfer modules run strictly downwards. Each rule
carries the reason it exists; the failure prints it. Type-only imports are
ignored: they are erased at build time and cannot form a runtime cycle.

**Bundle budget.** The eager entry chunk has a documented budget
(`EAGER_BUDGET_KB` in `vite.config.ts`), enforced by
`scripts/bundle-report.mjs`. `npm run bundle:report` builds and prints which
chunk holds which major dependency, marking each as eager (fetched before the
shell renders) or lazy. It fails if the entry chunk grows past the budget, or if
xterm, highlight.js or marked reappear in the eager graph — one static import
from a store is enough to undo the split, and nothing else would notice.

**CI jobs.** `check` (the full gate, Linux), `rust` (Ubuntu/macOS/Windows, so
the `cfg`-gated platform code keeps compiling and its portable tests keep
passing) and `msrv` (Rust 1.85.1 with `--locked`). Workflow permissions are
`contents: read`, and no job receives secrets.
